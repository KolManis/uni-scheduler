# ADR-0024: Миграции применяет приложение при старте (goose)

Принято · 2026-09-25

## Контекст
Миграции выполнял Postgres при создании тома (`docker-entrypoint-initdb.d`), а на рабочую базу их
накатывал `make db-migrate`. Список файлов миграций был продублирован в шести местах:
`docker-compose.yml`, `deploy/docker-compose.yml`, `scripts/package.ps1`, `Makefile`, `make.ps1`,
`deploy/README.md`.

Так появилась реальная ошибка: миграции 0007 и 0008 не были добавлены ни в одно из этих мест.
На новой базе, при установке из пакета и после `make db-migrate` колонок
`teachers.undesired_slots` и `schedules.run` не было бы, и приложение падало бы с
«column does not exist». Ошибку нашли вручную, а не проверкой.

Вторая слабость — база не знала, какие миграции в ней уже есть: `db-migrate` прогонял всё
подряд и работал, только пока каждая миграция написана с `IF NOT EXISTS`.

## Решение
- Миграции встроены в бинарник (`migrations/embed.go`, `go:embed`) и применяются приложением
  при старте через goose (`postgres.Migrate`), до приёма запросов. Применённые версии goose
  записывает в `goose_db_version`. Новая миграция — один файл в `migrations/`.
- **Базы, созданные до goose**, принимаются без пересоздания (`adoptLegacySchema`): если
  таблица `schedules` есть, а версия 1 не записана, 0001 отмечается как применённая без
  выполнения. Иначе goose начал бы с 0001, и её вставка демо-справочников упала бы на
  повторяющихся ключах. Остальные миграции идемпотентны и применяются поверх — так в старую
  базу доезжают и забытые 0007–0008.
- **Пакет для сервера**: `seed.sql` — дамп рабочей базы без строк расписаний (схема, справочники,
  `goose_db_version`). Сервер создаёт из него базу при первом запуске, приложение видит, что
  всё применено. Отдельная папка миграций в пакете не нужна.
- Все шесть списков миграций и `make db-migrate` убраны.

goose v3.27.0 — последняя версия, совместимая с Go 1.25: v3.28 требует Go 1.26.

## Альтернативы
- **Своя таблица версий и цикл по файлам** (~50 строк) — без зависимости, но самописно; goose —
  стандартный инструмент, понятнее при сопровождении.
- **Оставить initdb и завести один общий список** — не решает главного: база по-прежнему не
  знает, что в ней применено.

## Подтверждение
- `TestMigrate` (тег `integration`, временные базы в локальном Postgres): пустая база;
  повторный запуск; старая база без 0006–0008 с сохранённым расписанием; старая база со всеми
  колонками. Если отключить `adoptLegacySchema`, оба кейса со старой базой падают на повторной
  вставке демо-корпусов.
- Копия рабочей базы (33 расписания): «existing schema adopted as version 1», версии 1→8,
  все 33 расписания открываются. Затем так же — на самой рабочей базе; повторный старт: 8→8.
- Пакет: `seed.sql` новым способом развёрнут в пустую базу, приложение — 8→8, справочники на
  месте, расписаний нет.

## Последствия
- Добавить миграцию — положить файл в `migrations/` с `-- +goose Up`; пересобрать образ.
- Миграции теперь выполняются в транзакции (по умолчанию goose): упавшая миграция не оставляет
  базу наполовину изменённой.
- Пустая база без `make seed` по-прежнему получает демо-справочники из 0001.
