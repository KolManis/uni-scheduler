# ADR-0023: Воспроизводимый запуск — сиды и число раундов

Принято · 2026-09-24

## Контекст
Методы улучшения брали сид из текущего времени и останавливались по таймеру. Два запуска на
одних данных давали разные расписания, и ни один нельзя было повторить: ни чтобы разобрать
странный результат, ни чтобы подтвердить числа в отчёте. Записать только сид мало: за одно и то
же время поиск успевает сделать разное число шагов (другая машина, другая нагрузка).

## Решение
- Каждый запуск записывает `domain.RunInfo`: построение, метод улучшения, сид построения, сид
  улучшения и **число раундов улучшения**, которые он сделал. Хранится в `schedules.run`
  (миграция 0008), показывается на странице расписания.
- Повтор (`replayschedule`, кнопка «Повторить запуск», `POST /api/v1/schedules/{id}/replay`) берёт
  те же сиды и останавливается не по времени, а ровно на записанном раунде (`runBudget`, run.go).
- Раунд, который оборвало время, отбрасывается и не засчитывается: иначе повтор, не ограниченный
  временем, довёл бы его до конца и получил бы другое расписание.
- Многостарт: каждый старт получает свой сид улучшения, записывается запуск победителя.

## Альтернативы
- Всегда останавливаться по числу шагов — результат зависел бы от скорости машины по времени
  ответа, а пользователь задаёт именно таймаут.
- Сохранять только сид — повтор совпадал бы лишь случайно.

## Последствия
- Имитацию отжига точно не повторить: её температура зависит от прошедшего времени (`Exact: false`).
- Повтор совпадает, только если справочники и правила оценки с тех пор не менялись; иначе
  страница сообщает, что score отличается.
- Расписания, составленные до этого решения, повторить нельзя.

## Подтверждение
`TestReplayGivesSameSchedule`: на реальных данных для ILS, LNS, табу-поиска и генетического
алгоритма повтор с бюджетом 1 мс даёт те же пары и тот же score, что запуск на 2 с.
Проверено на PostgreSQL: запуск (131 раунд) и повтор совпали пара в пару.
