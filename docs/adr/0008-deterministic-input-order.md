# ADR-0008: Солвер сортирует входные данные перед построением

Принято · 2026-09-23 · `68fed7a`

## Контекст
Изредка генерация давала случайно плохой результат: один прогон — score 83 740 и 14 дней с
одной парой, около 20 других на тех же данных — 13–34 тыс. и 2–3 таких дня. По устройству
алгоритма так быть не должно: построение детерминировано, а iterated local search принимает
только улучшения.

## Причина
Построение зависит от порядка входных данных: при равных штрафах побеждает преподаватель, план,
аудитория или слот, встретившийся раньше. Запросы к БД идут без `ORDER BY`, и PostgreSQL не
гарантирует порядок строк.

Доказательство — построение без локального поиска на одних и тех же данных:

| Порядок | Score построения |
|---|---|
| как из БД, дважды | 240 600 и 240 600 |
| 4 случайных перестановки | 198 060 … 364 680 |

## Решение
`normalizeInput` сортирует справочники по ID в начале солвера. Сделано в солвере, а не в
запросах: результат не зависит от того, откуда пришли данные; порядок списков в интерфейсе не
меняется.

## Подтверждение
После исправления все 6 вариантов порядка дают одинаковое построение (303 760).
`TestSolveTeacher_InputOrderDoesNotMatter` падает без нормализации.
Бенчмарк 5 × 3: медиана 30,7–34 тыс. (до — 32–34 тыс.); другой порядок дал другой локальный
оптимум сопоставимого качества.

## Последствия
Результат воспроизводим. Разброс построения по порядкам (198–365 тыс.) показывает, что
многостарт по разным порядкам — перспективное улучшение.
