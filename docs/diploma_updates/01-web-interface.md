# Веб-интерфейс

**Было:** текст диплома описывает систему только как REST API. В `diploma_full.docx` в
заключении веб-интерфейс прямо назван перспективным направлением развития, то есть чем-то
несделанным: «...веб-интерфейс для работы без API...».

**Стало:** веб-интерфейс реализован (`internal/transport/http/web/*`) и является
полноценным вторым способом работы с той же бизнес-логикой, что и REST API — не
надстройкой поверх API по HTTP, а отдельным набором HTTP-обработчиков, вызывающих те же
методы `usecase.Service`, что и JSON-обработчики.

## 1. Новый пункт функциональных требований (гл. 1)

Предлагаю добавить в список ФТ (после существующего ФТ-7 «REST API»):

> **ФТ-8. Веб-интерфейс.** Система должна предоставлять браузерный интерфейс для работы со
> всеми справочниками и расписаниями без необходимости составлять HTTP-запросы вручную:
> создание, редактирование и удаление корпусов, кафедр, аудиторий, учебных групп,
> преподавателей и учебных планов; запуск генерации расписания с выбором алгоритма,
> тайм-аута и половины семестра; просмотр расписания в двух представлениях — по дням
> недели и по учебным группам; ручное редактирование отдельного занятия с немедленной
> проверкой жёстких ограничений HC1–HC3.
>
> **ФТ-9. Отчёт о неразмещённых занятиях.** По завершении генерации система должна
> вычислять и предоставлять пользователю список учебных планов, для которых не удалось
> разместить полный объём часов, с указанием дисциплины, типа занятия, преподавателя,
> задействованных групп, требуемого типа аудитории и числа недостающих часов.
>
> **ФТ-10. Просмотр расписания по учебным группам.** Система должна формировать
> представление расписания в разрезе учебной группы (сетка день × пара, аналогичная
> печатному расписанию на стену) с визуальным выделением «окон» — пропусков между двумя
> занятиями группы в один день, в отличие от пропусков до первого или после последнего
> занятия, которые окнами не являются.

## 2. Новый раздел архитектуры (гл. 2 / гл. 3)

Предлагаю добавить подраздел сразу после описания транспортного слоя REST API:

> ### Веб-интерфейс как второй транспортный адаптер
>
> Помимо REST API, транспортный слой включает пакет `internal/transport/http/web`,
> реализующий серверно-рендеренный веб-интерфейс. Архитектурно это отдельный HTTP-адаптер
> того же usecase-слоя: обработчики пакета `web` вызывают ровно те же методы
> `generator.Service` (`Generate`, `GetByID`, `List`, `Delete`, `PatchAssignment`), что и
> JSON-обработчики пакета `handlers`, различие — только в формате ответа (HTML вместо
> JSON). Это соответствует принципу чистой архитектуры: два разных способа доставки
> (delivery mechanism) не порождают дублирования бизнес-логики.
>
> Страницы рендерятся через стандартный пакет Go `html/template` без использования
> JavaScript-фреймворков и без сборки (Node.js/npm не требуются — интерфейс работает как
> часть единственного скомпилированного бинарного файла). Интерактивность (отправка форм и
> обновление части страницы без полной перезагрузки) реализована собственным облегчённым
> AJAX-скриптом (`static/app.js`, около 100 строк), понимающим HTML-атрибуты
> `hx-get`/`hx-post`/`hx-put`/`hx-delete` — по аналогии с библиотекой htmx, но без внешней
> зависимости; при необходимости скрипт можно заменить на настоящий `htmx.min.js` без
> изменения разметки шаблонов, поскольку используется только этот общий подмножество
> атрибутов.
>
> Каждый обработчик определяет, что вернуть — полную HTML-страницу или только фрагмент
> (используется при AJAX-обновлении части страницы), по заголовку запроса `HX-Request`,
> который скрипт `app.js` добавляет к каждому своему запросу. Это позволяет одному и тому
> же обработчику одинаково корректно обслуживать и прямой переход по ссылке (полная
> страница), и обновление части уже открытой страницы (только изменившийся фрагмент).
>
> Маршруты веб-интерфейса вынесены в отдельное пространство путей `/ui/*`, статические
> файлы (CSS, JS) отдаются из `/static/*` через `embed.FS` — они встроены в бинарный файл
> на этапе компиляции, отдельного каталога со статикой на сервере не требуется.

## 3. Таблица маршрутов веб-интерфейса (для таблицы 2.2 или отдельной новой таблицы)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | Редирект на `/ui/schedules` |
| GET | `/ui/schedules` | Список расписаний + форма генерации |
| POST | `/ui/schedules/generate` | Генерация расписания (форма) |
| GET | `/ui/schedules/{id}` | Просмотр расписания по дням недели |
| GET | `/ui/schedules/{id}/groups` | Просмотр расписания по группам с подсветкой окон |
| DELETE | `/ui/schedules/{id}` | Удаление расписания |
| GET/PATCH | `/ui/schedules/{id}/assignments/{idx}/edit` | Форма и сохранение переноса занятия |
| GET/POST/PUT/DELETE | `/ui/{buildings,departments,rooms,groups,teachers,subject-plans}` | CRUD-страницы справочников |

## 4. Уточнение к таблице REST API (гл. 2, таблица 2.2)

В существующей таблице REST-маршрутов отражено только чтение справочников (`GET
/teachers`, `/groups`, `/rooms`, `/subject-plans`). По факту API давно поддерживает и
запись — эти маршруты нужно добавить в таблицу (они не новые в коде, но в тексте диплома
их никогда не было):

| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/v1/{buildings,departments,rooms,groups,teachers,subject-plans}` | Создание записи справочника |
| PUT | `/api/v1/{...}/{id}` | Обновление записи справочника |
| DELETE | `/api/v1/{...}/{id}` | Удаление записи справочника |
| GET | `/api/v1/schedules/{id}/excel?type=all_groups` | Экспорт в Excel: все группы одним файлом (по аналогии с `all_teachers`) |
